SQL Injection Detective
SQL injection is the most historically common web application vulnerability. Four lessons — each shows vulnerable code, a live interactive query simulator, and two questions: identify the vulnerability and select the correct fix. Understanding SQLi means understanding how unsanitized input becomes a database command.
// THE CORE PROBLEM
# User types: ' OR '1'='1
# Query becomes:
SELECT * FROM users WHERE user=''
OR '1'='1' -- always true → dumps everything
// KEY CONCEPTS
WHY SQLI WORKS
SQL injection works because user input is concatenated directly into a SQL query string. The database can't distinguish between the developer's intended SQL and the attacker's injected SQL — they're the same string.
PARAMETERIZED QUERIES
The correct fix: use prepared statements / parameterized queries. The SQL structure is defined first with placeholders (?), then user input is bound separately. The database treats bound parameters as data, never as SQL commands — injection is structurally impossible.
INPUT VALIDATION vs SANITIZATION
Validation checks if input is acceptable (is this a valid email?). Sanitization removes dangerous characters (strip apostrophes). Validation and sanitization are defense-in-depth layers — but parameterized queries are the primary fix for SQLi.
WHAT SQLI CAN DO
Bypass authentication (login without credentials), extract the entire database (UNION attacks), modify or delete data (UPDATE/DELETE injection), execute OS commands (in some configurations). SQLi is an Integrity AND Confidentiality violation.
